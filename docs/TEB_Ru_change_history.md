# История изменений TEB-Ru: tau-схема, диагностический сад и сопутствующие правки

Документ содержит историю разработки tau-схемы потоков дороги и сада, диагностической
прокси-модели сада и сопутствующих правок, **с привязкой к нумерации коммитов**.
Кроме того, здесь собраны дефекты, не относящиеся к исходной модели: драйвера,
читалки форсинга и стендов (I1–I4, §5.5), численные дефекты собственных правок
(N1–N2, §5.6) и найденные, но не исправленные вопросы (C1–C5, §5.7).
Актуальное описание схемы — в `TEB_Ru_tau_scheme_T_CAN_reformulation.md` и
`TEB_Ru_garden_diagnostic_scheme.md`; список дефектов исходной модели — в
`TEB_Ru_source_defects.md`.

Ветка разработки: `MV_devs` (репозиторий `https://github.com/mkolennikova/TEB-Ru`).

---

## 0. Текущие (незакоммиченные) правки
**Разделение репозитория на `src_dev` и `src_ctrl` (рабочая копия).** Дерево источника
разделено на два независимых дерева, собираемых из корня репозитория: `src_dev/` — текущая
физика ветки `MV_devs` + I/O (`make -C src_dev` → `build/TEB_offline_dev.exe`), `src_ctrl/` —
физика первого коммита `582c3ab` + перенесённые из dev I/O и словники, с общими `namelist/`,
`input/`, `python/`, `docs/` (`make -C src_ctrl` → `build/TEB_offline_ctrl.exe`).

* I/O перенесён в `src_ctrl` целиком: единый `output/TEB_output.csv` (вместо 15 `.txt`),
  строгое чтение обоих словников (`NML_PRINT_DIAG` / `NML_REPORT_ABSENT`, `IOSTAT > 0` →
  STOP), CLI (`-forcing_nml`, `-param_nml`, `-output`, `-help`), `dt` в `/tebparam/`,
  `forc_step` в `/tebforcing/`, окно прогона `1..nsteps-1`, `INB_ATM = forc_step/dt`;
* ключи общего словника, которых у первого коммита не было, проводятся в его физику
  «минимальной проводкой»: `urb_z0_town` / `urb_zd_town` (резолвер форм `<знач>`, `<знач>m`,
  `<знач>H`, `H/<n>`; именованные схемы Macdonald не реализованы — громкий STOP),
  `urb_z0_gdn` / `urb_alb_gdn` / `urb_emis_gdn` / `urb_z0_grf` / `urb_alb_grf` /
  `urb_emis_grf` (носитель — `MODD_PROXI_SVAT_PAR`), `teb_type_garden` /
  `teb_type_greenroof` (`PROXY_*` принимаются, `EXT`/`EXT_NEU` → STOP). Значения по
  умолчанию совпадают с базовыми, поэтому словник без этих ключей воспроизводит первый
  коммит;
* при этом прогоне найдены и перенесены в `src_ctrl` два дефекта базовой физики — **D8** и
  **D9** (`TEB_Ru_source_defects.md`): неинициализированные альбедо/эмиссивность/радиационная
  температура зелёных поверхностей и неинициализированная `ZTS_GROUND`. Оба уже исправлены в
  `src_dev` и отсутствовали в первом коммите, поэтому на общем словнике (сад и кровля
  выключены) `src_ctrl` давал `NaN`/`SIGFPE` через несколько шагов. После переноса
  dev-реализации прогон `src_ctrl` проходит 17 999 шагов **с включённым
  `-ffpe-trap=invalid,zero`** без `NaN`/`Inf`;
* оба дерева пишут одинаковый набор модельных колонок в одном CSV-формате, что и позволяет
  сравнивать их построчно.

**Сверка `src_ctrl` с веткой `main` (побайтово, по blob-хешам).** `main` — отдельная линия
(расхождение с `MV_devs` в `35a2963`, tip `460a1c9`), исходники в ней лежат в корне
(`src_driver/`, `src_teb/`, …), обёртки `src/` там нет. Из 155 файлов исходников `src_ctrl`
**147 совпадают с `main` побайтово**; расхождений шесть, и они атрибутированы:

| файл | источник расхождения |
| --- | --- |
| `src_driver/sfc_teb.F90` | изменил сам `main` (неиспользуемый dummy `teb_lshade`, `dt` стал скаляром) — только интерфейс, на числа не влияет |
| `src_driver/call_driver.F90` | порт I/O-обвязки физики (Фаза A) + собственное изменение `main` |
| `src_driver/run_teb_offline.F90` | порт I/O автора + собственное изменение `main` |
| `src_proxi_SVAT/greenroof.F90` | только порт (`z0` кровли из неймлиста) |
| `src_teb/teb_garden.F90` | только порт (фикс D8) |
| `src_teb/urban_drag.F90` | только порт (Фаза A + фикс D9) |

Дополнительно `main`: не имеет ни unified `TEB_output.csv`, ни ключей `urb_z0_town` /
`urb_zd_town` / `urb_z0_gdn` …, т.е. **не может прочитать общий `namelist/namelist.nml`**
(9 неизвестных ключей = ошибка чтения), и **содержит дефекты D8/D9** (его
`teb_garden.F90`/`urban_drag.F90` побайтово равны первому коммиту), причём его собственный
неймлист задаёт `teb_lgarden=.FALSE.`, `fr_garden=0.0`, `teb_lgreenroof=.FALSE.` — ровно
вырожденную конфигурацию этих дефектов.

**Физическое расхождение с `main` при идентичных настройках — одно: режим оконных штор
(`LSHADE`).** В `main` (и `src_dev`) `LSHADE` — аргумент из ключа `teb_lshade` с дефолтом
`.TRUE.`; в первом коммите он жёстко `.FALSE.`. Ключ `teb_lshade` перенесён в `src_ctrl`
**по образцу `main`** (проводка `RUN_TEB_OFFLINE → TEB_INTERFACE → CALL_DRIVER`, где
`LSHADE` — аргумент, а жёсткое `LSHADE = .FALSE.` закомментировано), но с **дефолтом
`.FALSE.`**: неймлист без ключа воспроизводит первый коммит бит-в-бит (проверено — SHA-256
вывода совпал с прежним валидированным прогоном), а `teb_lshade=.TRUE.` включает шторы и
воспроизводит поведение `src_dev`/`main` (влияет на `TI_BLD`, `HVAC_COOL/HEAT`,
`H_TOWN`/`LE_TOWN`, `GFLUX_TOWN`). Отличие от `main` в объявлении: `teb_lshade` объявлен
`LOGICAL, DIMENSION(1)` (в `main` — скаляр), чтобы не опираться на нестандартное
согласование скаляр→rank-1 для dummy `LSHADE`.



**Диагностический прокси для зелёной кровли и настраиваемая `PHU` (рабочая копия).**
Тот же диагностический баланс энергии поверхности, что и у сада, теперь доступен для
зелёной кровли:

* новый ключ `teb_type_greenroof` (`'PROXY_OLD'` — исторический прокси Боуэна 0.5/0.5,
  `'PROXY_NEW'` — диагностический баланс `Rn = H + LE`, по умолчанию). Кровля — это
  поверхность крыши, поэтому обмен только с воздухом уровня форсинга (`PTA`/`PQA`/`PVMOD`
  на `PUREF`): ветви каньона и τ-расщепления нет;
* `GREENROOF` (`src/src_proxi_SVAT/greenroof.F90`) использует общий решатель
  `GARDEN_BALANCE` и нейтральные коэффициенты `GARDEN_PCD_NEUTRAL`/`GARDEN_PCH_NEUTRAL`;
* тепловая шероховатость кровли: новый ключ `urb_z0_o_z0h_grf` (по умолчанию `4.0`,
  `XZ0_O_Z0H_GR`);
* `PHU` обеих поверхностей вынесена в намлист: `urb_phu_gdn` (сад) и
  `urb_phu_grf` (кровля); значение применяется в **обеих** схемах
  (новая и старая). Решатель `GARDEN_BALANCE` получил аргумент `PPHU`;
* **ревизия дефолтов `PHU`.** По литературной оценке (β-фактор городской
  растительности и экстенсивных кровель, FAO-56 `Ks`, ISBA `hu`) дефолты обоих
  ключей заданы как **`0.7`**: сад — типичный непереувлажнённый газон, кровля —
  экстенсивный седум (без дневной «конденсационной» аномалии при `PHU < RH`).
  **В базовой версии модели** значения были `urb_phu_gdn = 0.8` и
  `urb_phu_grf = 0.3`. Поэтому **сравнение с базовой версией теперь нужно делать,
  задавая в неймлисте `urb_phu_gdn = 0.8` и `urb_phu_grf = 0.3`** (иначе прогоны
  не воспроизводимы по `LE`/`H` и по бюджету влажности города);
* диагностики кровли добавлены в `TEB_output.csv` (`TS_GREENROOF`, `RN_GREENROOF`,
  `H_GREENROOF`, `LE_GREENROOF`, `EVAP_GREENROOF`, `QSAT_GREENROOF`, `PHU_GREENROOF`,
  `PAC_AGG_GREENROOF`); замыкание `RN = H + LE` проверено на уровне машинного нуля.
* режимы **EXT/EXT_NEU** для зелёной кровли (по аналогии с садом, без эмулятора):
  кровля задаётся извне через штатный интерфейс `EXT`, а диагностические
  коэффициенты обмена считает `URBAN_DRAG` — тип EXT по полному `URBAN_EXCH_COEF`
  (устойчивость, `z0h = urb_z0_grf/urb_z0_o_z0h_grf`, `WIND_THRESHOLD`), тип EXT_NEU
  по нейтральной формулировке внутренней схемы (`PCD = PCDN > PCH`, `PRI` не
  определён, `ZZ0H_GREENROOF_ATM` — использованная тепловая шероховатость). Тип
  EXT/EXT_NEU принудительно включает `teb_lgreenroof_ext`. Новые колонки CSV:
  `PAC_GREENROOF_ATM`, `PCD_GREENROOF_ATM`, `PCDN_GREENROOF_ATM`, `PCH_GREENROOF_ATM`,
  `PRI_GREENROOF_ATM`, `ZZ0H_GREENROOF_ATM` (проверено аналитически:
  `PCDN = (kappa/ln(PUREF/z0))**2`, `PCH = PCDN*ZFH`, `PAC = PCH*max(PVMOD, XVMIN_GD)`;
  у типа EXT `PRI` определён и коэффициенты ниже нейтральных, как у сада);
* исправлена опечатка во внешней ветви кровли (`ZRN_GD` -> `ZRN_GR`) и увеличена
  длина имён колонок CSV (`out_names` 16 -> 24), из-за которой имя
  `PAC_AGG_GREENROOF` обрезалось до `PAC_AGG_GREENROO`.

**Эмулятор внешней зелёной кровли `PCD_GREENROOF` в offline-драйвере.** Режимы
`'EXT'`/`'EXT_NEU'` кровли (см. выше, в реестре — №25, №26) до сих пор не были
проверены физически: интерфейс `EXT` не имел «внешней модели», и сопоставить
экспортируемые коэффициенты с потоками было не с чем. Теперь offline-драйвер сам
играет роль внешней модели кровли (contained-подпрограмма `PCD_GREENROOF` в
`src/src_driver/run_teb_offline.F90`, по образцу `PCD_GARDEN` сада):

* кровля — поверхность крыши: **одна** ветвь обмена, с воздухом уровня форсинга
  (высота `hlev_teb`, `PVMOD`), каньонной ветви и τ-расщепления нет. Поэтому нет и
  ковариационной поправки τ-осредования: `CH_eff = PCH` тождественно, так что
  `CH_eff·max(V*,Vmin) ≡ Ca` точно (у сада `CH_eff` вбирает член
  `τ(1−τ)(Cd_C−Cd_A)(V_A−V_C)`);
* коэффициенты — нейтральные: `GARDEN_PCD_NEUTRAL(hlev_teb, z0_gr)` и
  `GARDEN_PCH_NEUTRAL(hlev_teb, z0_gr, urb_z0_o_z0h_grf)`, т.е. те же, что у
  внутренней кровли `'PROXY_NEW'` и те же, что экспортирует `URBAN_DRAG` в режиме
  `'EXT_NEU'`. В режиме `'EXT'` экспортируемые коэффициенты несут поправку
  `URBAN_EXCH_COEF` (устойчивость, `HZ0H = 'MASC95'`), поэтому их отличие от
  `EMU_GR_*` — мера этой поправки: в стенде `max|d|` составляет `3.1e-3` (`PCD`),
  `2.3e-3` (`PCH`), `6.6e-3` (`PAC`);
* радиация берётся прямо из форсинга драйвера (`SW = (swdir_s+swdifd_s)·(1−fr_panel)`,
  `LW = lwd_s·(1−fr_panel)`): крыша не затеняется каньоном и не облучается его
  переотражениями (`URBAN_SOLAR_ABS`: `PREC_SW_RF = (dir+sca)×(1−fr_panel)`,
  `ZREC_LW_RF = PLW_RAD`), поэтому, в отличие от сада, восстанавливать поглощённую
  радиацию из `XABS_SW`/`XABS_LW` не требуется. Добавок панелей нет: стенд
  работает при `teb_lsolar_panel = .FALSE.`;
* новые колонки CSV (13, только в режимах `EXT`/`EXT_NEU`): `EMU_GR_CD`, `EMU_GR_CH`,
  `EMU_GR_CA`, `EMU_GR_V`, `EMU_GR_T`, `EMU_GR_Q`, `EMU_GR_PSW`, `EMU_GR_PLW`,
  `EMU_GR_TS`, `EMU_GR_RN`, `EMU_GR_H`, `EMU_GR_LE`, `EMU_GR_EVAP`. Предел
  `nout_max` поднят `128 -> 192`: 13 колонок `EMU_*` сада вместе с 13 колонками
  `EMU_GR_*` кровли в 128 не помещались;
* стенд `python_tests/greenroof_emu_compare.py` (3 морфологии × 3 режима кровли,
  сад выключен, `dt = forc_step` — тогда одна строка CSV равна одному подшагу
  модели и лаг виден) проверяет:

  | проверка | результат |
  | --- | --- |
  | замыкание `EMU_GR_RN = EMU_GR_H + EMU_GR_LE` | `6.4e-12` Вт/м² |
  | лаг связи `TS_GREENROOF[k] = EMU_GR_TS[k-1]` (то же для `H`, `LE`, `EVAP`) | `0.000e+00` |
  | тождества `EMU_GR_CD = PCD_GREENROOF_ATM`, `EMU_GR_CH = PCH_GREENROOF_ATM`, `EMU_GR_CA = PAC_GREENROOF_ATM` (режим `'EXT_NEU'`) | `0.000e+00` |
  | спин-ап связи: `H_GREENROOF[0] = LE_GREENROOF[0] = 0` (`Ts` первой строки — температура воздуха начала прогона) | `0.000e+00` |
  | эмулятор против внутренней схемы `'PROXY_NEW'` в той же строке (`EMU_GR_TS/H/LE/EVAP/RN`) | `1.1e-13` K, `9.9e-13`, `8.0e-12`, `3.2e-18`, `6.8e-13` Вт/м² |
  | прогностические колонки `'EXT_NEU'` против внутренней схемы со сдвигом на строку | `1.1e-13` K, `9.9e-13`, `8.0e-12`, `3.2e-18` |
  | `'EXT'` против `'EXT_NEU'`: эмулируемые `EMU_GR_*` совпадают, экспортируемые `*_GREENROOF_ATM` различаются | `0` и `3.1e-3`/`2.3e-3`/`6.6e-3` |

  Всего 126 проверок, 96 содержательных — все пройдены (остальные — справочные:
  отличие `'EXT'` от `'EXT_NEU'` и `Ts` спин-апа). Внутренняя схема `'PROXY_NEW'`
  воспроизводится эмулятором **бит-в-бит** (кроме строки 0 — спин-ап связи), при
  этом прогностические колонки отстают ровно на один подшаг. Структурной ошибки,
  в отличие от сада (`PAC_GD = 0`), у кровли нет: каньонной ветви у неё вообще нет.

**Убрана избыточная величина `PAC_AGG_GARDEN` (`ZAC_AGG_GD`): влажность каньона считается
той же проводимостью сада, что и его температура.** В обеих ветвях репозитория величина
`PAC_AGG_GARDEN`/`ZAC_AGG_GD` встречалась только в паре с множителем влажности
`PHU_AGG_GARDEN` и физически всегда совпадала с `PAC_GARDEN`:

* `src_ctrl` (внешний сад `EXT`): `PAC_AGG_GARDEN` остаётся `0.` из прокси и эмулятором не
  перезаписывается (`ZAC_AGG_GD = XUNDEF`), поэтому узел **температуры** каньона получал
  слагаемое `PAC_GD·ZGD`, а узел **влажности** — нулевой садовый вклад: неявная связь сада
  с каньоном была несогласованной;
* `src_dev`: прокси `'PROXY_NEW'` и τ-схема `GARDEN_TAU` присваивают
  `PAC_AGG_GARDEN = PAC_GARDEN`, а `'PROXY_OLD'` — `0.`, то есть собственной физики у
  величины нет;
* в COSMO-TEB `PAC_AGG_GARDEN = PAC_GARDEN` присваивается **до** пересчёта `PAC_GARDEN` в
  `URBAN_DRAG`, поэтому узел влажности читал неинициализированный вход.

Правка: узел влажности каньона в `avg_urban_fluxes.F90` обеих ветвей использует
`PAC_GD·PHU_AGG_GD` — ту же проводимость, что и узел температуры. Dummy-аргумент удалён из
`modi_avg_urban_fluxes`/`avg_urban_fluxes`, `teb_garden` (`ZAC_AGG_GD`), `modi_garden` и
`garden` (интерфейс и реализация, включая вызовы `GARDEN_PCD`/`GARDEN`), `teb_garden_struct`
и `modi_teb_garden_struct`, `call_driver`, `sfc_teb` и из вызовов `GARDEN_PCD` в
`run_teb_offline.F90`; диагностическая колонка `PAC_AGG_GARDEN` (`dev`-цепочка
`teb_garden → teb_garden_struct → call_driver → run_teb_offline`) удалена из вывода.
Множитель влажности `PHU_AGG_GARDEN` (`PHU_GARDEN`) сохранён.

Проверки:

* базовый прогон `src_ctrl` — 35 колонок, вывод **побайтово** равен прежней валидированной

## 1. Правила ведения

Общие требования к документации (состав файлов, формат, ссылки, маркировка правок в
коде, проверки перед коммитом) собраны в `TEB_Ru_documentation_rules.md`
(на английском); здесь приведены только правила этого файла.

* **Нумерация.** Каждой записи присвоен сквозной номер `№N` (нумерация — «номер
  коммита» в этой истории). Хеш коммита приводится в сокращённом виде и ссылкой
  вида `https://github.com/mkolennikova/TEB-Ru/commit/<sha>`; порядок записей —
  топологический (как в `git log`), дата — дата автора коммита.
* **Что включено.** Все содержательные коммиты ветки, начиная с того, где появились
  ключи `urb_z0_town`/`urb_zd_town` (№1), и до текущего состояния.
* **Что исключено.** Автоматические коммиты-контрольные точки редактора
  (`cline checkpoint session=…`, десятки штук) — они не несут содержания и
  создаются при каждой сессии. Их отсутствие в реестре нормально: пропуски
  хешей между записями — именно они.
* **Пометка «локальный»** означает, что коммит пока не отправлен в `origin`, и
  ссылка на GitHub для него не работает до `git push`.
* **Связь с документами.** В записи указано, какие разделы документации появились
  или изменились в этом коммите; в схемных документах обратные ссылки даны на
  номера записей этой истории.
* **Стенды.** «Сутки» — прогон на форсинге ERA5 для Москвы, `dt = 300 с`.
  Морфологии: `LCZ2` (плотный каньон, `H/W = 1.5`, `H = 20 м`), `LCZ9`
  (`H/W = 0.15`, `H = 6 м`), `SPARSE` (`H/W = 0.0086`). Иное указывается явно.
* **Внешние материалы.** Скрипты и данные, которых нет в репозитории
  (`check_physics.py`, `check_extneu.py`, `mk_nml.py`, `run_only.py`, `cmp_runs.py`,
  `plot_tau05.py`, драйверы песочницы `test_garden*.F90` + `build.ps1`), находятся в
  рабочем каталоге стендов (`D:\TEB_work\...`) — они упомянуты как источник чисел,
  но не входят в репозиторий. Скрипты из `python_tests/` — часть репозитория.

### №1 · [`788ea00`](https://github.com/mkolennikova/TEB-Ru/commit/788ea00) · 2026-09-14 · `feat(urban): add z0/zd namelist entries and Macdonald1998 scheme`

**Что сделано.** В намлист добавлены внешние параметры `urb_z0_town` (шероховатость)
и `urb_zd_town` (высота вытеснения) с формами записи: метры, доля высоты здания
(`'0.1H'`), деление высоты (`'H/3'`), имя параметризации. Реализована схема
Macdonald et al. (1998) в вариантах для упорядоченных (`A = 4.43`, `β = 1.0`) и
квадратных (`A = 3.59`, `β = 0.55`) массивов зданий, считающая `z0` и `zd` по
плотностям застройки:

```
d/h  = 1 + A^(−λp)·(λp − 1)                                           eq. (23)
z0/h = (1 − d/h)·exp( −( 0.5·β·(Cd/κ²)·(1 − d/h)·λf )^(−0.5) )        eq. (22)
```

где `λp = urb_fr_bld`, `λf = mean(teb_fai)`, `Cd = 1.2`, `κ = 0.4`. Оба ключа
разрешаются независимо, поэтому схему можно комбинировать с явным значением во
втором ключе.

**Попутно устранён дефект официального TEB** (D7 в `TEB_Ru_source_defects.md`):
в официальном коде высота вытеснения не является параметром, а задаётся жёсткой
поправкой `+ urb_h_bld/3.` (эквивалент `zd = 2/3·H`), что противоречит его же
ветровому профилю (`H − zd` даёт `zd = 1/3·H`). В TEB-Ru обе части используют
одно значение `urb_zd_town`.

**Документация.** `TEB_Ru_variables_description.md`, раздел «Urban Aerodynamics»
(формы записи, формулы Macdonald, сопоставление с официальным TEB).

### №2 · [`42638ab`](https://github.com/mkolennikova/TEB-Ru/commit/42638ab) · 2026-09-14 · `feat(output): single CSV output file with the forcing used at each step`

## 5. Неиспользуемые варианты, прочие дефекты и открытые вопросы



В этом разделе собрано то, что рассматривалось в ходе работы, но не вошло в
реализованную схему. Материал перенесён из прежних ревизий схемных документов
(в частности из прежней редакции tau-документа, где они составляли «часть II») и из
тел коммитов.

### 5.1 Исходная τ-схема дороги (v1, №4): аномалия каньона ∝ τ

В v1 τ взвешивал **вес дороги в бюджете воздуха каньона** (`A_rd_w = τ·A_rd`),
поэтому доля дороги в бюджете равнялась `τ·A_rd/(τ·A_rd + A_wl + A_gd + A_top)` и
при доминировании остальных членов падала пропорционально τ. Измерения (SPARSE_w0,
BEM включён, трафик 0):

| величина | τ = 1 (референс) | τ = 0.0192 (v1) |
| --- | --- | --- |
| доля дороги в бюджете каньона | 0.124 | 0.0027 |
| `ΔT_can`: вклад дороги | 0.77 K | 0.02 K |
| `ΔT_can`: вклад стен и антропогенных потоков | 0.11 K | 0.11 K |
| `ΔT_can` всего | **0.874 K** | **0.145 K** |

Физически `T_CAN` в TEB — температура воздуха приземного слоя, к которой применима
теория подобия: над прогретой поверхностью средняя температура слоя выше
температуры на уровне форсинга на величину порядка `θ*/κ` (для стенда 0.2 K для
LCZ2 … 0.9 K для SPARSE), и референсная формулировка именно такие аномалии и даёт.
Схема v1 при τ → 0 эту аномалию снимала («каньон без аномалии»), что искажало
`T_CAN` как диагноз приземного воздуха и меняло потоки стен и окон (они «видели»
более холодный воздух). Это стало причиной ревизии v1.1 (реализованной в №5).

### 5.2 Вариант R-A v2 (не реализован)

**Идея.** τ трактуется как **затенённость дороги каньоном** и интерполирует
**сопротивление** обмена «поверхность дороги ↔ воздух каньона» между затенённым
значением (`1/A_rd`) и незатенённым (`1/A_atm − 1/A_top`); весь поток дороги при
этом выделяется в приземный воздух и уходит из объёма через вентиляцию `A_top`.

```
R1_s   = 1/A_atm − 1/A_top
R1(τ)  = τ/A_rd + (1−τ)·R1_s
A_1(τ) = 1/R1(τ)                       (проводимость дорога↔воздух каньона)
H_ROAD = ρ·cp·A_1(τ)·(T_rd − T_c)      (в стационаре = ρ·cp·A_series(τ)·(T_rd − T_a))
```

Свойства варианта: при `τ = 1` тождественно исходный код; при `τ = 0` полная
проводимость ровно `A_atm`; аномалия `ΔT_can` сохраняется (`≈ θ*/κ` при
`A_top ≈ κ·u*`, на стенде согласие ~4 %); вес дороги в бюджете каньона равен
`A_1(τ)`. Оценки по стенду: полная проводимость `A_atm/A_series0` ≈ 1.25–1.26 для
разрежённых кейсов, `ΔT_can` для SPARSE ≈ 0.9 K вместо 0.145 K.

**Главное допущение, из-за которого вариант требовал отдельной валидации:**
`A_rd`, `A_top`, `A_atm` трактуются как три сопротивления **одного и того же** слоя,
так что тождество `1/A_atm = R1_s + 1/A_top` осмысленно. В коде это три разные
параметризации (разные ветры и шероховатости), поэтому `R1_s` — сетевая оценка,
требующая численной проверки (`A_can_s > A_rd`, `κ·u*/A_top ≈ 1`, guard
`A_atm ≥ A_top`). **Реализовано не было:** задача была решена иначе — ревизией
«трёх температур» (№5), которая сохраняет аномалию не через сопротивление, а через
второй крайний член `T_CAN1` по теории подобия.

### 5.3 Отвергнутые подварианты

| вариант | суть | почему отвергнут |
| --- | --- | --- |
| Линейная версия R-A (`A_eff = τ·A_rd + (1−τ)·A_atm` при `ZT_REF = T_c`) | ранняя попытка сохранить аномалию | член `(1−τ)·A_atm·(T_rd − T_c)` берёт проводимость всего слоя `A_atm` (её пара — `T_a`), а разность температур — только до воздуха каньона: некорректная пара «проводимость ↔ эталонный воздух», завышенный поток |

### 5.4 Снятые с эксплуатации режимы

* **Заглушка Боуэна для сада (`'PROXY_OLD'`)** — историческая схема, сохранена

### 5.5 Дефекты драйвера, читалки форсинга и стендов (I1–I4)

Эти дефекты **не относятся к исходной модели**: они затрагивали драйвер TEB-Ru,
читалку форсинга и стенды. На физику они не влияли, но делали результаты
непригодными для проверок (или мешали запуску). Раньше они описывались в
`TEB_Ru_source_defects.md`; в этот файл отнесены, потому что дефектами исходного TEB
не являются.

**I1. Переполнение массива имён колонок CSV (№6).** Имена колонок писались в массив
с пределом `nout_max = 64`, а к моменту правки вывод достиг 66 колонок: массив
переполнялся, и строка заголовка портилась — появлялись лишние поля и терялось имя
последней колонки. Исправление: предел 128 и явная проверка `nout > nout_max`.

**I2. Нестрогое чтение намлиста (№16).** При неудачном `READ` группы
(`IOSTAT > 0`) драйвер печатал предупреждение и продолжал работу; все элементы,
объявленные **после** сбойной записи, молча сохраняли значения по умолчанию
драйвера. Воспроизведённый случай: `python/forcing_utils.py` записывал
`teb_hour = 0.0` (вещественное значение для INTEGER-элемента) — чтение обрывалось на
нём, и `teb_month`/`teb_year` оставались дефолтными `2004`/`2`, т.е. модель считала
солнечную позицию и календарь BEM **февраля 2004** вместо даты форсинга, без единого
сообщения об ошибке. Исправление: неудачное чтение останавливает прогон; элементы
даты (`teb_year/teb_month/teb_day/teb_hour/teb_min`) и `nsteps` без значений по
умолчанию; диагностика печатает все объявленные элементы группы с номерами строк;
лог эхо-печатает стартовую и конечную дату, `nsteps`/`forc_step`, `dt`; добавлены
колонки `SOLAR_ZENITH`, `SOLAR_ELEV`, `SOLAR_AZIM`. Проверка: 10/10 тестов матрицы
строгого чтения, `check_solar_position.py` — ALL PASS, результаты модели бит-в-бит.

**I3. Координаты точки в ответе CDS (№7, №16).** Точечные временные ряды CDS могут
отдавать координаты точки (`latitude`, `longitude`) скалярными
**data-переменными**, тогда как читалка ожидала координаты: `convert_nc2df` падал с
«Dataset does not contain 'latitude'/'longitude'» и прогон не запускался. Обе формы
теперь принимаются. Проверено на ERA5-точке для Москвы (55.7N, 37.5E), январь 2024:
744 шага, 238 снежных часов, 40.1 мм снегозапаса.

**I4. Графики стенда читали диагностики референсного прогона (№12).** В
`python_tests/compare_tau_scheme.py` дополнительные кривые читались из референсного
прогона: для форсинга это верно (он входной и одинаков), но `T_CAN0` и `T_CANYON`
различаются между прогонами, и рисунки вводили в заблуждение. Кривые τ-прогона
теперь берутся из него самого.

### 5.6 Численные дефекты собственных правок (N1–N2)

**N1. Первая версия τ-агрегации дороги (№4).**

1. **`SIGFPE` при нулевой водяной проводимости.** Эталонная влажность `ZQ_REF`
   вычислялась как отношение по водяным проводимостям, и на сухой дороге деление на
   ноль давало `SIGFPE` на разрежённых конфигурациях (LCZ9/SPARSE). Исправление:
   `ZQ_REF` (и `ZT_REF`) используются только там, где соответствующая эффективная
   проводимость `> 0`; при нуле берётся каньонный эталон, что для исчезающего потока
   эквивалентно.
2. **`PTAU` как explicit-shape массив.** В `TEB` массив веса был объявлен
   explicit-shape, что несовместимо с передачей срезов; требуется assumed-shape
   (`DIMENSION(:), INTENT(IN)`).

Обе правки — численные, а не физические: они не меняют результатов там, где расчёт
считается, а лишь делают его корректным на вырожденных конфигурациях.

**N2. Ветвевые диагностики снега на дороге читались до записи (№8; найдено при работе
над тепловой шероховатостью сада, запись №24).**

* **Суть.** В `TEB_GARDEN_STRUCT` четыре диагностики снеговой ветви τ-схемы
  (`PHSN_RD_CAN`, `PHSN_RD_ATM`, `PLESN_RD_CAN`, `PLESN_RD_ATM`) были объявлены
  **локальными автоматическими массивами** и передавались в `TEB_GARDEN`, где
  `TEB_GARDEN2` → `AVG_URBAN_FLUXES` (узлы `T_CAN0`, `T_CAN1`, `Q_CAN0`, `Q_CAN1`)
  **читает** их в начале вызова, а `TEB` → `URBAN_SNOW_EVOL` **записывает** в конце
  того же вызова. Автоматический массив не сохраняется между вызовами, поэтому воздух
  каньона получал **мусор стека**, умноженный на снежную долю дороги `PDN_RD`
  (строки `+ ZRD·PHSN_RD_CAN·PDN_RD/ρ/cp` в `PT_CAN0`, `+ ZRD·PHSN_RD_ATM·PDN_RD` в
  `ZH_CAN1`, `+ ZRD·PLESN_RD_ATM·PDN_RD·XLVTT/XLSTT` в узле влажности).
* **Следствия.** (1) *Физика:* вклад снега на дороге в воздух каньона был произвольным;
  при `PDN_RD = 0` (лето, все стенды серии А) слагаемые равны нулю, поэтому проверки
  «бит-в-бит» и тождества были чистыми и дефект не проявлялся. (2) *Устойчивость:*
  когда в мусоре оказывались `NaN`/`±Inf`/очень большие значения, прогон падал
  незакономерно — `SIGFPE` (деление на ноль, сравнение с `NaN`) или `SIGSEGV`, при
  одном и том же входе примерно в 1 прогоне из 4…10 (зависит от раскладки памяти,
  что и делало картину «плавающей»).
* **Исправление.** Диагностики перенесены в постоянную структуру `DIAG_MISC_TEB_t`:
  `DMT%XPHSN_RD_CAN`, `DMT%XPHSN_RD_ATM`, `DMT%XPLESN_RD_CAN`, `DMT%XPLESN_RD_ATM`
  (`modd_diag_misc_tebn.F90`: компоненты и `NULLIFY`; `alloc_teb_struct.F90`:
  `ALLOCATE` **с обнулением**; `dealloc_teb_struct.F90`: освобождение).
  `TEB_GARDEN_STRUCT` загружает их из `DMT` перед `CALL TEB_GARDEN` и сохраняет
  обратно после него; в `TEB_GARDEN` и `modi_teb_garden.f90` их `INTENT` изменён с
  `OUT` на `INOUT` (они читаются раньше, чем пишутся). В результате узел каньона
  видит снежный обмен **предыдущего** подшага — так же, как остальные ветвевые
  диагностики, живущие в структурах (`PAC_ROAD_ATM`, `ZZ0H_ROAD_ATM` и т.д.).
* **Проверка.** Сборка с `-fcheck=all -finit-real=snan -finit-integer=-999999`
  до правки падала **детерминированно**: `SIGFPE` в `avg_urban_fluxes.F90`
  (`gdb`: `bt` → `avg_urban_fluxes` ← `teb_garden` ← `teb_garden_struct` ←
  `call_driver`), а печать слагаемых показала `PHSN_RD_CAN = NaN`; после правки та же
  сборка проходит. Репродьюсер короткого кейса (24 шага, SPARSE, форсинг репозитория):
  **4 падения из 8** до правки и **2 из 20** после — остаточная частота объясняется
  второй причиной (C5), она **диагностирована**: дефект тулчейна (`setlocale` UCRT +
  libgfortran), см. §5.7 и §5.8. *Влияние на числа:* в синтетическом снежном кейсе (форсинг
  репозитория + искусственный снегопад 1e-4 кг/м²/с, `PDN_RD` до 0.7) эталонная и
  исправленная сборки (при `urb_z0_o_z0h_gdn = 1`, т.е. без эффекта `z0h`) дали
  **бит-в-бит** одинаковый результат: в тех прогонах стек оказался нулевым, поэтому
  дефект проявлялся не значениями, а падениями. Это ожидаемо: свежие страницы стека
  нулевые, а «грязный» мусор появляется при другом порядке вызовов (другая
  конфигурация/количество слоёв), что и даёт либо искажённые снежные слагаемые, либо
  `NaN` и падение.

### 5.8 Обход дефекта тулчейна (C5): `setlocale` и libgfortran

   дописывающие метку в файл (в обход буферизации stdout). У упавшего прогона
   последняя метка — сразу после чтения группы `tebparam`, и в логе нет только строки
   `dt = …`: значит падает `WRITE(*,'(A,F10.1,A,F12.1,A,I0,A)')`. Одного этого шага
   мало: любые добавленные операторы сдвигают раскладку кучи и «прячут» падение
   (частота — 1–2 прогона из 25).
2. **Стабильные адреса.** Сборка с `-Wl,--disable-dynamicbase`: бэктрейс
   воспроизводится, и `addr2line` резолвит кадры exe: `#14` — тот самый `WRITE`
   (`run_teb_offline.F90:961`), `#13/#12` — `libgfortran-5.dll`, `#7…#11` —
   `ucrtbase.dll`.
3. **Векторный обработчик исключений** (`AddVectoredExceptionHandler(1, …)`,
   маленький внешний объект на C, подключённый к линковке) пишет в файл код исключения,
   адрес отказа, вид доступа, регистры, адреса стека и список модулей процесса.
   Для падения: вид доступа `0` (**чтение**), `fault_pc = ucrtbase+0x2383`,
   `rsi` — адрес сразу за закоммиченной частью кучи, кадр-вызыватель
   `ucrtbase+0x331c`.
4. **Резолв по таблицам экспорта PE**: смещения `0x2383` и `0x2ca6/0x2f4a/0x2faf/0x331c`
   принадлежат `setlocale` (байтовый скан строки имени локали), а в таблице импорта
   `libgfortran-5.dll` есть `setlocale` и `localeconv`.
5. **Изолированная проба** (внешняя: чистый C, вне репозитория, без TEB-Ru) воспроизводит
   паттерн, который libgfortran использует при форматированном выводе вещественных:

```c
saved = setlocale(LC_NUMERIC, NULL);   /* указатель во внутренний буфер UCRT */
setlocale(LC_NUMERIC, "C");            /* UCRT освобождает буфер -> saved висячий */
/* здесь вывод числа через snprintf и т.п. */
setlocale(LC_NUMERIC, saved);          /* разбор освобождённой памяти как имени локали */
```

   Вывод пробы:

```
1) setlocale(LC_NUMERIC,NULL) -> 0000013BC641BB04 'C'
2) setlocale(LC_NUMERIC,C)    -> 0000013BC641E614 'C'
3) saved after reuse: 0000013BC641BB04 (bytes: 3b 01 00 00) ';'
```

   то есть по адресу `saved` лежит уже не строка `'C'`, а переиспользованная память;
   если в ней до конца закоммиченной области кучи нет нуля, скан внутри `setlocale`
   уходит в незакоммиченную страницу — `SIGSEGV`. Это объясняет и нестабильность
   (содержимое зависит от раскладки и тайминга), и то, почему падение исчезает от
   любых правок кода, от `-fcheck=all`, от `-finit-*` и от отладчика.

**Обход (проверен, включается автоматически).** Обёртка лежит в репозитории
(`src/src_driver/wrap_setlocale.c`), а `src/Makefile` подключает её сам: при сборке на
Windows компилятором, содержащим `gfortran`, libgfortran линкуется статически и его
обращения к `setlocale` направляются в `__wrap_setlocale` (для запроса `name = NULL`
возвращается указатель на постоянный буфер — он не может стать висячим). На других
системах обход не включается: glibc и рантайм macOS хранят имя локали в статической
памяти, поэтому описанный дефект там невозможен. Выбор можно переопределить явно:

```sh
make -C src FC=gfortran                 # Windows: обход включается сам
make -C src FC=gfortran WRAP_LOCALE=1   # включить принудительно
make -C src FC=gfortran WRAP_LOCALE=0   # выключить (эталонная сборка)
```

Сборка печатает выбранный режим (`WRAP_LOCALE: on/off`), а при `FC=ifort` обход не
применяется и печатается предупреждение: рантайм Intel не использует libgfortran.
Короткий кейс SPARSE (24 шага, постоянный выходной каталог):

| сборка | падений |
| --- | --- |
| сборка без обхода (libgfortran как DLL) | 4 / 60 и 7 / 60 |
| `-static-libgfortran` без обёртки (контроль на той же раскладке) | 12 / 100 |
| с обходом (`WRAP_LOCALE` включён; на Windows — по умолчанию) | **0 / 100**, автоматическая сборка — 0 / 30 |

MD5 `TEB_output.csv` у всех трёх сборок совпадает с эталоном, то есть обход меняет
только время жизни указателя локали, а числа — бит-в-бит. Альтернативы: другой рантайм
(не проверено — msvcrt-сборки на машине нет) или исправление в GCC (issue в upstream).

**Предел τ = 1** (`teb_ltau_scheme = .FALSE.`, тот же сайт): коэффициенты
вырождаются точно в модельные (`EMU_CH_EFF = EMU_CD_EFF = EMU_CH_NAIVE = 0.013831 =
(κ/ln(3/0.1))²`), но расхождение с внутренней схемой растёт: средняя
Δ`H_GARDEN` = −16.9, Δ`H_TOWN` = −5.8 Вт/м², Δ`T_CANYON` = +0.18 K. Причина —
структурное отличие режима `EXT`: `PAC_GD = 0`, поэтому сад не входит в неявные узлы
`T_CAN0`/`Q_CAN0`.

**Худший случай осреднения — τ = 0.5** (LCZ6: `H = 10 м`, `H/W = 0.5`, 32 суток):

| величина | эмулятор − честная схема (τ = 0.5) | сама τ-схема (τ = 0.5 против τ = off) |

τ-схемы (−10.7 Вт/м²) и складывается из конвенции смешивания (`T* = T_CAN` вместо
Ca-взвешенной смеси), структурного `PAC_GD = 0` и одноподшагового лага.

**Регрессия.** Прогоны `PROXY_NEW`/`PROXY_OLD` (τ вкл/выкл) остаются **бит-в-бит**
(код закрыт условием `teb_type_garden == 'EXT'`); прогон `EXT` меняется по замыслу
(59 из 96 столбцов). Первый подшаг — спин-ап связи (`Ts = T` воздуха, потоки
нулевые), его желательно исключать из статистики.

### А.8 Проверки при τ = 0.5

Чтобы получить «худший случай» τ-осреднения при любой морфологии, порог
tanh-релаксации берётся равным H/W сайта (`teb_tau_hw_thresh = urb_h2w`): тогда
`tanh(0) = 0` и `τ = 0.5` **точно**. Набор: LCZ2 (H/W = 1.5), LCZ6 (0.5),
LCZ9 (0.15), SPARSE (0.0086) — по три-четыре прогона (`честный внутренний сад`,
`EXT`-эмулятор, `EXT_NEU`-эмулятор, база τ = off).

Проверки постановки: τ, восстановленная из потоков ветвей честного прогона, равна
`0.500000` на всех четырёх сайтах; тождество `H = τ·H_CAN + (1−τ)·H_ATM` —
`max|d| = 2–4e-12` Вт/м²; `EMU_TAU = 0.5`; `max|Ca(честный) − Ca(EXT_NEU)| = 0`
(бит-в-бит, 767 шагов × 4 сайта); τ-агрегат `EMU_CA_EFF` нейтрального экспорта равен
τ-агрегату честной схемы с точностью 1e-17 м/с.

Ошибки эмулятора против честной схемы (среднее/rmse за месяц; для `Ts` — K) и
эффект самой τ-схемы (τ = 0.5 против τ = 1):

| сайт | `Ts` (`EXT` / `EXT_NEU`) | `H_GARDEN` (`EXT` / `EXT_NEU`) | `LE_GARDEN` (`EXT` / `EXT_NEU`) | эффект τ-схемы (`H` / `LE` / `Ts`) |
| --- | --- | --- | --- | --- |
| LCZ2 | +0.176 / +0.158 | −3.98 (rmse 5.13) / −3.46 (4.80) | +2.77 (4.78) / +2.21 (4.50) | +27.0 / −31.2 / +1.00 |
| LCZ6 | +0.041 / +0.004 | −4.59 (5.41) / −3.00 (4.20) | +4.21 (6.38) / +2.66 (5.05) | +10.7 / −13.0 / +0.49 |
| LCZ9 | +0.018 / −0.019 | −6.09 (7.55) / −4.09 (5.81) | +5.86 (8.69) / +4.01 (6.76) | +1.9 / −3.9 / +0.37 |
| SPARSE | +0.019 / −0.013 | −5.97 (7.79) / −4.12 (6.15) | +5.84 (9.00) / +4.17 (7.19) | −0.6 / −1.1 / +0.31 |

Выводы:

1. **Нейтральный экспорт ближе к честной схеме**: `|bias|` по `H_GARDEN` падает на
   13–33 % (LCZ6: 4.59 → 3.00 Вт/м²), rmse — на 6–23 %, по `Ts` — с 0.041 до 0.004 K.
   Причина: эмулятор сам решает баланс по нейтральным коэффициентам, а `EXT` отдаёт
   ему коэффициент с `Ri` и `z0h`, которого эмулятор не воспроизводит.
2. Остаточная ошибка **структурная**, а не от τ-осредования (ковариационный член
   снят тождественно): единая смесь `T* = T_CAN`, отсутствие неявной связи сад↔каньон
   в режиме `EXT` (`PAC_GD = 0`) и лаг в один подшаг. При τ = 0.5 на LCZ6 эмулятор
   забирает примерно половину эффекта τ-схемы (rmse 5.4 против 10.7 Вт/м²); на
   разрежённых LCZ9/SPARSE сам эффект τ мал (1–2 Вт/м²), и остаточные ≈6 Вт/м² его
   превышают.
3. Ошибка не является сдвигом по времени: корреляция `H_GARDEN` максимальна при
   нулевом лаге (≈1.000), распределение ошибки сосредоточено в дневные часы.
4. В режиме `EXT` разложение на ветви **не эмулируется**: обе ветви несут один и тот
   же поток, тогда как честная схема даёт реальные ветви, различающиеся на LCZ6 при
   τ = 0.5 на 40–60 Вт/м².

Графики стенда (`plot_tau05.py`): суточный ход `Ts`/`H`/`LE`/проводимости по 4 сайтам
и 4 прогонам (fig1), суточный ход ошибки эмулятора рядом с эффектом τ-схемы (fig2),
почасовые диаграммы рассеяния с линией 1:1 (fig3), 8 суток почасовых рядов LCZ6 с
панелью Δ`H`/Δ`LE` (fig4), сводка bias/rmse против эффекта τ-схемы (fig5), ветви
честной схемы против «плоского» потока эмулятора, корреляции по лагу, квантили и
ошибка по часам (fig6).

## 8. Как восстановить прежнее состояние

* Любая версия схемы — по коммиту из реестра (§2):
  `git show <sha>:<путь>` (просмотр) или `git checkout <sha>` (переключение).
* **Важно:** до коммита №20 (`5e2cd79`) документы лежали **в корне репозитория**,
  а не в `docs/`, и исходники — в `src_teb/`, `src_driver/`, `src_proxi_SVAT/`,
  `src_struct/`. Примеры:

```
git show 991c2bd:TEB_Ru_tau_scheme_T_CAN_reformulation.md      # документ до раскладки по каталогам
git show c37b29c:TEB_Ru_garden_diagnostic_scheme.md
git show 41f0271:src_teb/avg_urban_fluxes.F90                  # код до раскладки
```

* Ветку с номерами коммитов можно сравнить с текущей: `git log --oneline MV_devs`,
  `git diff <sha> -- docs/`.
* Данные CAPITOUL (вынесены из репозитория в №21):
  `git restore --source=main --worktree "CAPITOUL DATA"`.
